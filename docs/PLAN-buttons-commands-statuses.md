# План работ: кнопки, меню команд и статусы активности в MAX

Документ фиксирует задачи, постановки и решения по платформе MAX.
Источник задач — Руслан Строгов.

## 1. Инлайн-кнопки (clarify и подтверждения)

**Проблема.** Функционал кнопок был заложен, но не работал.

**Причина.** Плагин не переопределял точки входа, через которые gateway
запрашивает кнопки — `send_clarify` и `send_slash_confirm`. Вызывались
базовые заглушки из `gateway/platforms/base.py`, которые отдают
нумерованный список текстом: сообщение уходит без вложения, и MAX
кнопок не рисует. Низкоуровневый `send()` умел собирать
`inline_keyboard`, но до него дело не доходило.

**Решение.**
- `_send_inline_buttons()` — сборка вложения `inline_keyboard`
  (`{"type": "inline_keyboard", "payload": {"buttons": [[...]]}}`,
  кнопка `{"type": "callback", "text": ..., "payload": ...}`).
- `send_clarify()` — по кнопке на каждый вариант + `✏️ Свой вариант`,
  payload `cl:<clarify_id>:<idx>`.
- `send_slash_confirm()` — `✅ Один раз` / `🔒 Всегда` / `❌ Отмена`,
  payload `sc:<once|always|cancel>:<confirm_id>`.
- `_resolve_button_payload()` + обработка в `_handle_message_callback` —
  нажатие возвращается именно в тот prompt, из которого нарисована
  клавиатура (`resolve_gateway_clarify` / `slash_confirm.resolve`).

## 2. Меню команд у поля ввода

**Проблема.** Кнопки вызова меню команд в MAX нет.

**Причина.** `MAXClient.set_commands()` не существовал, хотя адаптер его
вызывал: `AttributeError` глотался в `except`, в лог шло «Failed to
register bot commands (non-fatal)». Плюс список был из двух заглушек.

**Решение.**
- `MAXClient.set_commands()` → `PATCH /me/commands`
  (`GET`/`POST`/`PUT` по этому пути отдают 404).
- `_build_menu_commands()` — список берётся из единого реестра Hermes
  (`hermes_cli.commands`), того же, что питает меню Telegram. Добавили
  команду в ядро — она автоматически появилась в MAX.
- Локальная заглушка `/help` убрана: справку отдаёт сам Hermes.
  `/start` оставлен как приветствие со ссылкой на меню.

**Ограничения MAX Bot API** (проверено вживую):
- не более **32** команд (`Field 'commands' size (100) must be at most 32`);
- описание — не более **128** символов;
- прочитать список обратно нельзя: `GET /me/commands` → 404.

## 3. Статусы активности («печатает…», «отправляет фото…»)

**Проблема.** Индикатор «печатает» не виден ни в личке, ни в группе
(какое-то время работал).

**Причина.** Для действий в MAX нужен **реальный `chat_id` чата**, а
адаптер подменял его на `user_id` для личных диалогов (это правильно для
`/messages`, но не для `/chats/{id}/actions`). В логах видно
`send_typing to chat_id=23676002` — то есть на user_id. MAX такой запрос
принимает и отвечает `200`, но индикатор не отображает — поэтому
выглядело как «молча не работает».

**Решение.**
- Сохраняем исходный `typing_chat_id` до подмены `chat_id = user_id` и
  адресуем индикатор реальному чату (в т.ч. `_last_message_ids`).
- `send_action(chat_id, action)` — общий best-effort метод статусов.
- Статусы по контексту: `sending_photo` перед загрузкой фото,
  `sending_file` перед отправкой документа, `typing_on` — пока агент
  думает и работает над задачей.

**Поддерживаемые действия** (проверено): `typing_on`, `sending_photo`,
`sending_video`, `sending_file`, `sending_audio`, `mark_seen`.
**Не поддерживаются**: `typing_off`, `typing` → `400 proto.payload`.

## 4. Слэш-команды в группах

**Проблема.** В группе «/команда» не срабатывала.

**Причина.** `_should_reply()` в группах требует упоминания бота или
триггер-слова, а MAX присылает команду из меню без `@бота` — сообщение
отсекалось.

**Решение.** Сообщения, начинающиеся с `/`, пропускаются и в группах.
Гейтинг самих команд остаётся на стороне Hermes.

## 5. Прочее, починенное по ходу

- **Защита от эхо**: бот не отвечает на собственные сообщения
  (`_bot_user_id` + проверка в `_should_reply`).
- Дубль в названии камеры в постах архива (`Canon Canon …` → `Canon …`).
- Крон-задачи под новую модель: в профиле `max` прибиты к
  `deepseek/deepseek-v4.1-flash`; в профиле `default` прибиты 6 задач,
  у которых оставался снапшот старой модели (`deepseek-v4-flash`) —
  их гейт «Skipped to prevent unintended spend» пропускал.

## 6. Локализация служебных сообщений (русский) и одно сообщение прогресса

**Проблема.** Агент присылал английские технические статусы
(«Working — 18 min — iteration 5/90, receiving stream response»), причём
**каждый апдейт — новым сообщением**, из-за чего чат забивался.

**Причина.** Ядро обновляет «пульс» прогресса через
`adapter.edit_message(...)`, а у MAX-адаптера этого метода **не было** —
он падал в fallback и слал новое сообщение на каждое изменение.
В Telegram это работает потому, что адаптер умеет редактирование.
Плюс сам текст формируется в ядре по-английски.

**Решение.**
- `edit_message()` / `delete_message()` в адаптере.
- ВАЖНО: MAX понимает только query-форму —
  `PUT /messages?message_id=<mid>`, `DELETE /messages?message_id=<mid>`.
  Вариант с mid в пути (`/messages/{mid}`) отдаёт `404 method.not.found`
  (проверено вживую: путь — 404, query — 200). Исправлено и в клиенте.
- `_ru_status()` — перевод служебных строк на границе адаптера: пульс
  «⏳ Работаю — N мин», «итерация X/Y», названия инструментов
  (`terminal` → `терминал`), фразы-статусы. Обычный текст ответов
  не переписывается — замены узкие.
- Конфиг `display.platforms.max`: `tool_progress_grouping: accumulate`,
  `cleanup_progress: true` — служебный пузырь один и убирается после
  финального ответа.

**Ограничения MAX API** (проверено): редактирование и удаление — только
через query-параметр `message_id`; чтение — `GET /messages/{mid}` (путь).

## 9. КОРНЕВАЯ ПРИЧИНА: устаревшая копия `max_shared` в site-packages

Самая важная находка. В venv лежала **установленная копия пакета
`max_shared`** (`hermes-agent/venv/Lib/site-packages/max_shared`, от 21 сен).
При импорте `from max_shared.max_client import MAXClient` Python идёт по
`sys.path`, где `...venv\Lib\site-packages` стоит **раньше** каталога
плагина (он добавляется в конец). Поэтому загружалась старая копия, и все
правки в копии плагина **не действовали в рантайме**.

Отсюда оба симптома:
- `set_commands` — «'MAXClient' object has no attribute 'set_commands'»
  (в логе от 18:15) → меню команд не регистрировалось;
- `edit_message`/`delete_message` со старым путём `/messages/{id}` → 404 →
  ядро не могло править «пузырь» прогресса и слало новый на каждый апдейт.

На диске **четыре** копии `max_shared`:
```
hermes-agent/venv/Lib/site-packages/max_shared   <- выигрывает при импорте
plugins/max-hermes-plugin/max_shared             <- git-репозиторий
plugins/max-platform/max_shared
profiles/max/plugins/max-platform/max_shared     <- рабочая копия профиля
```

**Решение:** синхронизировать все копии. После правки — обязательно чистить
`__pycache__` и **перезапускать gateway**, иначе остаётся старый модуль в
памяти. При добавлении новых методов в `max_shared` обновлять копию в
site-packages в первую очередь — иначе изменения молча не подхватятся.

## 11. Отклик-«реакция» на сообщения пользователя — РЕАЛИЗОВАНО

**Задача (постановка Руслана).** Бот должен ставить реакции на сообщения
собеседника:
- принял информацию → один знак;
- занят, идёт много сообщений → другой;
- сделал сразу / готово → третий.

### Главное ограничение: MAX Bot API не умеет ставить реакции

Проверено трижды:
1. Живой перебор эндпоинтов — `GET/PUT/POST /messages/{mid}/reactions`,
   `PUT /reactions` → **404 method.not.found**.
2. Официальная OpenAPI-спецификация
   (`github.com/max-messenger/api-schema`, файл `schema.yaml`) — слова
   `reaction` в ней **нет вообще**. Все доступные пути:
   `/me`, `/me/commands`, `/chats/{chatId}`, `/subscriptions`, `/uploads`,
   `/messages`, `/messages/{messageId}`,
   `/messages/{messageId}/comments`, `/videos/{videoToken}`, `/answers`,
   `/updates`.
3. Строка «Likes/dislikes» в документации — это пример сценария (голосование
   кнопками), а не метод API.

**Вывод:** поставить эмодзи-реакцию на чужое сообщение бот технически не
может. Это ограничение платформы, не наша недоработка.

### Что API всё-таки даёт

| Возможность | Статус |
|---|---|
| Поставить реакцию на сообщение | ❌ нет метода |
| Ответить реплаем на сообщение (`link: {type: reply, mid}`) | ✅ 200 |
| Редактировать СВОИ сообщения (`PUT /messages?message_id=`) | ✅ 200 |
| Комментарий к сообщению (`POST /messages/{mid}/comments`) | ⚠️ только в каналах, в личке → «Comments are not available for this chat» |

### Предлагаемое решение — «пузырь-реакция»

Собираем эффект реакции из того, что доступно:

1. На входящее сообщение бот отвечает **реплаем** (визуально «прикреплено»
   к сообщению пользователя) коротким текстом с эмодзи:
   - `👍 Принял` — информация принята, действий не требуется;
   - `⏳ Работаю` — взял в работу;
   - `✅ Готово` — задача выполнена.
2. **Один и тот же пузырь редактируется** по ходу дела, а не плодится новый.
   Адаптер уже хранит mid своих сообщений в `_last_message_ids[chat_id]`,
   а `edit_message` работает — механика готова.
3. Итоговый ответ агента приходит отдельным сообщением (или тем же, если
   ответ короткий и влезает в пузырь).

Так пользователь видит «реакцию» на своём сообщении и её смену по статусу,
и при этом в чате остаётся **одно** служебное сообщение, а не вереница.

### Маппинг состояний

| Событие | Эмодзи | Когда |
|---|---|---|
| Сообщение принято, работы нет | 👍 | мгновенный ack, простой вопрос/инфа |
| Начал работу над задачей | ⏳ | пришло сообщение, агент запустился |
| Работа идёт (несколько шагов) | ⏳ → счётчик | обновление того же пузыря |
| Готово | ✅ | финальный ответ отправлен |
| Ошибка | ⚠️ | задача не выполнена |

### Что нужно решить перед реализацией

- [ ] Формат: реплай-пузырь (прикреплён к сообщению) или отдельная строка статуса?
- [ ] Не дублировать ли индикатор «печатает…» (он уже сигналит «занят»)?
- [ ] Объём: делать ли реакцию на КАЖДОЕ сообщение или только когда агент
      реально уходит в работу?
- [ ] Настраиваемость: вкл/выкл и выбор эмодзи — через `config.yaml`.

**Приоритет: средний.** Реализуемо только в форме реплая с редактированием.
Прямые реакции ждём со стороны MAX — если метод появится, переключимся.

## 13. Кнопки для вопросов и команды в ответах

**Постановка Руслана.** Вопросы, где нужен его выбор, выводить кнопками —
текст он пропускает. Плюс команды, которые ему нужно выполнить, давать
готовыми кнопками, чтобы только нажать.

### Вопросы → кнопки

Штатный механизм — инструмент `clarify`: варианты ответа рендерятся как
callback-кнопки, нажатие возвращается в ожидающий prompt. Реализовано
(см. раздел 1). Важно: gateway **не** резолвит clarify из текста, если ответ
начинается с `/` — считает это командой. Поэтому команды и вопросы не
конфликтуют: вопросы идут через callback, команды — как текст.

### Команды в ответах → кнопки

В MAX есть тип кнопки **`message`** — нажатие отправляет её текст как
сообщение пользователя. Это и есть кликабельная команда. Типы кнопок MAX:
`callback`, `clipboard`, `open_app`, `link`, `message`, `request_contact`,
`request_geo_location`.

**Реализация.** `_extract_command_buttons()` в адаптере вынимает из ответа
агента строки, целиком состоящие из команды (`/status` или
`- /status — описание`), и превращает их в кнопки `message`. Нажатие
доставляет команду в чат — её достаточно нажать.

Защита от ложных срабатываний:
- строки внутри блоков ```` ``` ```` не трогаются;
- пути (`/usr/bin`, `/path/to/file`) не распознаются как команды, т.к.
  после первого сегмента нет разделителя `—`, `–`, `-` или `:`;
- не более 8 кнопок на сообщение;
- если ответ состоял только из команд, добавляется подпись
  «Нажми, чтобы выполнить:»;
- если у сообщения уже есть кнопки (clarify/confirm), авто-разбор не
  запускается.

**Проверено вживую:** нажатие кнопки `/status` доставило команду в чат —
значит механизм рабочий. Есть и `clipboard` — копирует текст в буфер.

## 8. Бэклог — низкий приоритет

### 8.1 Полная локализация сообщений Hermes на русский

MAX — русскоязычный мессенджер, поэтому **все** служебные строки должны
быть по-русски, включая ошибки. Сейчас на границе MAX-адаптера
(`_ru_status`) переведена только часть — самые частые статусы прогресса;
время от времени всплывают непереведённые строки.

Собрать и перевести:
- статусы прогресса и «пульс» (`gateway/run.py`);
- подтверждения и busy-ack («Interrupting current task», «Steered into
  current run», очередь/steer);
- ошибки доставки, таймауты, сообщения платформы;
- служебные ответы команд (`/status`, `/usage`, `/model` и т.п.);
- строки инструментов и подсказки clarify.

Как делать:
- искать кандидатов в `gateway/*.py`, `agent/*.py`, `tools/*.py`
  по литералам, которые уходят в чат;
- переводить **на границе адаптера**, чтобы не менять поведение других
  платформ (Telegram/Discord и т.д.);
- либо использовать штатный механизм фраз:
  `display.status_phrases` → каталоги `status_phrases.yaml` рядом с
  `HERMES_HOME` (режимы `append` / `replace`) — он покрывает
  long-running-статусы, но **не** строку «⏳ Working — N min, iteration…».

**Приоритет: низкий. Сначала функции.**
